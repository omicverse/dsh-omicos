# 0006 — Official membership lifecycle is domain- and account-bound

The published billing contracts distinguish a domain membership's `expires_at` from a short-lived plan token's TTL. They also distinguish purchased memberships from trial, promo, administrator and laboratory-seat grants. OmicOS OSS uses the official membership/reminder reads directly; it does not derive renewal notices from local clocks, a plan token or a stale purchase row.

The Host projects only documented lifecycle fields from `/api/billing/subscriptions` and `/api/billing/expiry-reminders`. Boolean values from the existing SQLite-backed server may be JSON booleans or exact numeric 0/1 and normalize to booleans; other ambiguous values, duplicate domains, invalid dates, malformed lists and unknown reminder states fail explicitly. Errors are not transformed into an empty/free membership list. Additional server fields and credentials are not forwarded by these projections.

The workbench shows server-provided expiry notices after cloud login and a separate per-domain membership panel in the store. Notices can be dismissed in the current window; changed records/new windows can show them again. Renewal buttons select the corresponding catalog domain, not a payment action. Grants are labelled and seat-derived memberships direct users to laboratory management. Unknown/not-supported/authentication failures are displayed separately from verified absence. None of this changes local data, history, kernels or BYOK permissions.

Cancel/restore requires explicit human confirmation naming its domain and existing expiry. The current official server reads the domain from a query parameter, not the JSON body. Before an explicit-domain mutation, the Host checks that the subscription read acknowledges exactly that domain; an older server that ignores the query is rejected before POST. Account generation is checked across that preflight as well as the existing request/owner-CSRF/rendered-account fences. The server still owns the atomic mutation and any concurrent membership changes; no unsupported subscription-version CAS contract is invented. Default-domain actions retain the server's default-domain semantics.

Each new membership read is bound to its rendered account and cancellation signal. A late old-account response is rejected in the Host and ignored after component disposal. Domain-specific detail requests also carry a local request sequence and target-domain check. Quote results carry the complete current purchase selection in the client; changing domain, period, provider, seats or laboratory invalidates the visible/confirmable quote even if its old response arrives late. The confirmation explicitly identifies the target domain. A rejected/unknown action never automatically retries checkout or a charged scientific task.

Refresh occurs on the active view, focus, explicit refresh, a membership-change event and a bounded foreground interval. Hidden-store timers stop; hidden documents skip refresh triggers. Successful payment and subscription actions request new membership/reminder data. No background OS notification, auto-renewal purchase, scheduled agent, real payment or entitlement inference is created.

Verification includes public DTO normalization/malformed-data tests, delayed account-change reads, wrong-domain/older-server rejection without POST, authenticated HTTP query-domain cancel/restore, stale-window identity rejection, and browser tests of expiry selection, labelled grants, cancel/restore without checkout, stale detail/quote responses and mobile overflow. All merchant behavior remains covered by isolated fixtures; real staging callbacks/credentials are a separate release gate.
