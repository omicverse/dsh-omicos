# 0007 — Discover capabilities before assuming a runtime contract

An extension-friendly workspace needs to distinguish implemented adapters from installed scientific dependencies and verified platform support. The owner-authenticated capability document (`omicos.capabilities/1`) describes the actual package version, accepted public scientific protocol and feature conditions. Discovery neither opens a language process nor contacts official cloud; configured Python/R paths are explicitly not proof that their packages work.

Feature states distinguish available implementation, configured-but-unprobed interpreters, optional Host/cloud services, unavailable features and unverified platform deployments. SSH/SLURM, dependency provisioning and native desktop bridges are not advertised as completed. Harness tools remain conditional on the actual Host ToolRuntime/approval services; a configured chat adapter still requires a model provider. Core compatibility mode does not advertise the disabled OSS Scientist.

API clients may send `x-omicos-protocol`. An unsupported explicit version returns HTTP 426 after owner authorization and before CSRF/body/action dispatch. Discovery itself remains reachable with a mismatched version so a client can diagnose compatibility. Missing headers preserve existing protocol-1 clients, including EventSource and ordinary artifact links; this is compatibility with the existing version, not permission to execute newer semantics by fallback. The React API helper sends version 1 and never retries/falls back after 426.

The diagnostic section can open even if session loading fails, preventing version rejection from hiding the recovery information. The Agent read tool exposes the same document. Standalone `--version` reads installed package metadata without opening a project; packed-product verification ensures metadata resolves from the published layout. Future protocol/schema changes still require explicit versioned adapters and validation; this mechanism does not provide runtime downloading or rollback on its own.

Checks cover owner protection, incompatible-version rejection before cloud actions, continued authorized discovery after rejection, client no-fallback behavior, honest cold-interpreter discovery, Core/Host distinctions, actual ToolRuntime registration, packed metadata/CLI version and the workbench diagnostic view.
