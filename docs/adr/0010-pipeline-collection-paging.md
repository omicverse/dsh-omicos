# 0010 — Pipeline collections page independently from selected work

The initial local Pipeline executor listed only 100 recent runs and loaded every definition on each list refresh. That hid older run IDs from the workbench and scaled ordinary metadata transfer with the full definition collection. The existing immutable definition and exact-run APIs remain authoritative; collection discovery now uses independent bounded cursors.

The list contract still returns `definitions` and `runs` arrays, capped at 50 summaries each, plus `definitionPage` / `runPage` totals and next row-ID cursors. Titles/IDs can be searched; run queries also match start-operation IDs and can filter recorded run state. Totals refer to the full collection, not filtered matches. Native SQLite JSON projections return scalar identity/status fields and attempt/checkpoint counts; code, outputs, input evidence and recovery arrays are retrieved only through exact definition/run/receipt reads. Missing definition references remain visible as an unavailable title instead of silently hiding the run. This is metadata projection, not verification that every saved scientific claim is valid.

Reopening a Pipeline service scans only persisted unfinished states in bounded batches before marking them interrupted. It does not deserialize all completed historical run journals, launch their workers or retry a previously used start operation. A start ID already bound to an archived run retains that exact run, including interrupted/failed status. This change does not alter human gates, checkpoint validation, file reservations, generation fencing, approval or cancellation ownership.

The workbench keeps selected run and editable definition state independent of the displayed pages. A selected ID outside the current search/page remains a labelled current option. Paging/filtering never replaces a draft, starts an analysis or cancels a held kernel. Users can open a full run UUID or definition SHA-256 directly, including older IDs. A changing run selection fences delayed poll responses, so a previous run's response cannot overwrite the newly selected detail. Existing optimistic revisions continue to gate sensitive actions.

The Agent state tool exposes the same collection cursors/query filters; exact-ID callers keep full evidence reads. No record is deleted to enforce a page window and no database schema change is required. A page is not a global transaction snapshot during concurrent new records. Individual large run journals/checkpoint arrays still use the full detail API; collection paging does not claim that per-run attempt history, retention/deletion or FTS indexing is complete.

Tests page 121 immutable definitions and 130 runs, preserve oversized journals behind exact reads, reject invalid cursors/states and recover an unfinished run older than 130 completed records without an interpreter. Owner-authenticated HTTP tests page and locate archived runs before login. The browser creates 55 additional definitions after a real checkpointed workflow, pages to the original definition without changing its saved draft, filters the current run out of the list and reopens its exact UUID without recomputation.
