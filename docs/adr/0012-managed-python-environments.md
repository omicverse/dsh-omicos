# ADR 0012: Hash-locked managed Python environments

Status: implemented for POSIX Python environments. Base interpreter/runtime-binary download, public scientific lock catalogs, Windows/Electron and R provisioning remain separate work.

## Decision

Each project owns a private schema-1 SQLite environment ledger and unique fixed venv directories. An installation request declares a title and at most 200 exact package/version records with SHA-256 wheel hashes. Requests are immutable, normalized and deduplicated by stable operation ID. Empty packages create a base venv without fetching scientific dependencies. No existing system or project environment is modified; venv does not inherit system site packages. The configured external Python supplies venv/ensurepip. Absolute venv paths are never renamed after creation.

Packages install with `--require-hashes --only-binary=:all:`; all transitive requirements must be explicitly locked. The default index is public PyPI; arbitrary indexes, URLs, editable installs, version ranges, source builds and requirement-file options are rejected. An optional project-relative offline wheel directory is resolved through workspace privacy/containment checks. Only regular wheel files are copied to private staging; HTML files, symlink wheel entries and oversized staging are rejected. Offline pip uses only this staging directory with `--no-index`.

The installer inherits the existing deliberate OS/library/proxy environment projection, removes Python/Conda environment overrides, disables pip configuration and never receives arbitrary Host/cloud credentials. `pip check` verifies dependency consistency. Before ready, a base `Python -I -S` process reads distribution metadata and hashes environment files, bytecode, configuration and executable bytes without loading the installed environment's site hooks. Directory symlinks are pinned; file links cannot escape except the standard venv base-Python executable links. Limits are 300000 files / 20 GiB of verification bytes. The lock pins downloads and the manifest detects later changes; it does not establish publisher trust, sandbox code, capture the shared base standard library/OS or establish scientific validity.

## Lifecycle and rollback

One installation/verification owns the project manager at a time. A responsive Node supervisor owns the POSIX process family and a separate Host-lifetime socket; installed processes never inherit that socket. Cancellation waits for actual process close. Host shutdown/interruption records a nonselectable partial installation. Host SIGKILL closes the socket and kills the actual installer family; restart recovers unfinished records as interrupted and never resumes them. Existing project-lock stale grace remains intact. Log tails are bounded to 64000 characters; commands have a 30-minute timeout.

Ready environments are never selected automatically. A separate human operation chooses a ready environment or external Python for the **next Host start**, with revision CAS, stable retries and immutable selection history. Current Python objects and already-started Pipelines keep their interpreter. Selected managed Python workers and Python Pipelines run in Python isolated mode (`-I`) so Host PYTHONPATH/user-site overrides do not leak into the managed import path; receipts record this flag. Workers disable bytecode writes so ordinary imports do not invalidate the installed-file manifest. At next start, manifest validation occurs before the project service is exposed; new Python and local Python Pipeline workers use the selected interpreter. Failed validation blocks Python execution and new Python Pipelines while retaining the workbench/history/rollback interface. It never silently falls back. Pipeline recovery still verifies its original environment and requires explicit acceptance of changes.

Only inactive failed/canceled/interrupted environment files can be explicitly removed. Metadata/logs and operation deduplication remain; replaying an old removed install request never recreates it. Ready/selected environments cannot be removed through this interface. Public Agent tools only read discovery/logs/history; installing, canceling, selecting and removing require explicit owner/CSRF workbench actions. This remains trusted OS-user execution: packages, pip and import hooks can execute code when authorized.

## Evidence and limits

Actual offline wheel tests cover byte hashes, installed package execution, live namespace preservation, next-Host selection/rollback, invalid locks and offline sources, cancellation and interruption. Tamper tests add a malicious `.pth`; verification detects changed files without executing the hook, and restart blocks fallback while the workbench still permits explicit rollback. Native baseline runs include Node 22.13.1. Chrome creates a real base venv, waits for ready, saves selection and rollback, reads history and confirms existing Python variables are preserved. A compiled CLI lifecycle fixture kills the Host during a real Python installer and verifies process death plus interrupted recovery after lock grace. An explicitly requested online fixture downloaded and imported the hash-pinned public `packaging==24.2` wheel in a temporary environment; it is not in default tests and does not certify every scientific package/platform lock. Temporary environments are removed after tests.
