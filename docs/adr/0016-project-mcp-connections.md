# ADR 0016: Project-owned MCP configuration, concrete Scientist scope and Host-owned authorization

Status: implemented against the optional published Harness 0.2.1-rc.3 MCP plugin. OAuth/A2A, external server package installation and unsupported MCP protocol extensions remain separate work.

## Reuse and scope

The Host dynamically loads the exact public `@deepseek-ai/dsh-mcp-client@0.2.1-rc.3` peer only when a human-enabled project connection has a live OmicOS Scientist. Harness owns stdio negotiation, Streamable HTTP, discovery, tool naming/results, resource providers and bounded reconnect. OmicOS does not bundle another MCP SDK or create another model loop. The shared Scientist preset is deliberately not the registration scope: its scoped `agent/created` listener attaches each concrete `agent.ctx` using the session's canonical workspace (or explicit Host workspace override). Other agents/projects do not acquire these tools or server instructions. Existing profile-managed MCP instances are not modified.

Each project has a private schema-1 SQLite registry of immutable config revisions, current pointers and stable operation receipts. Up to 50 saved / 10 enabled servers are supported, with at most 100 process arguments, 30 credential bindings and bounded configuration/timeout. Local process cwd is the actual project; arguments are passed by the Harness transport without implicit shell interpolation. An owner can explicitly choose any executable, including a shell, so this is not a sandbox or an executable allowlist. Server names exclude double/trailing underscores to avoid ambiguous tool-prefix ownership. Remote endpoints require credential-free HTTPS or explicit loopback HTTP, without embedded query credentials/fragments.

## Human authority and copied project files

Saving always disables the connection; enabling/disabling/reconnecting requires owner authentication, CSRF, current revision, stable operation ID, a human note and explicit confirmation. Reconnect creates a new revision, so retrying its operation does not repeatedly replace the transport. Existing operation receipts return current state and never reapply historical enablement.

Current access grants live in a separate private Host `mcp-authorization.sqlite`, keyed by canonical workspace, connection ID and exact current record digest. The project record's `enabled` flag alone grants nothing. Copying a project to another workspace/Host, restoring a pre-revocation project backup or replaying an old enable operation cannot restore revoked access. The workbench shows missing Host authorization and permits an explicit fresh decision. The authority database and its WAL/SHM are excluded from project file/import paths.

Mutations revoke the Host grant first, commit the project record second and grant the new enabled revision last. A failure/crash between these databases fails closed. If project commit succeeds but grant persistence fails, retry returns the committed record without silently granting access; a fresh human authorization is required. This deliberately favors closed access over claiming a cross-database atomic transaction. A user/program with full Host-user filesystem access remains outside this application trust boundary.

Credential bindings contain only Host environment variable names and optional standard authentication prefixes. Values resolve only from the Host plugin's explicit `mcpSecretEnvNames` allowlist. Arbitrary plaintext credential objects and interpreter/loader environment overrides are rejected. Values are not persisted or returned by connection APIs, exports, diagnostics or Agent state tools. Owner-provided command arguments/endpoint paths may still contain sensitive text and are not automatically redacted; exports disclose that limit. Stdio inherits the verified Harness subprocess environment behavior, not scientific-worker environment isolation, and runs with normal Host-user permissions. The SDK can start a temporary negotiation probe before the serving process; startup and external side effects are not exactly once.

## Calls, lifetime and diagnostics

Managed MCP tool and resource calls require Harness approval, preserving existing stronger denials and approval requirements. The dispatch guard also checks the current independent Host grant and record revision, including when another policy already requests approval. A save/disable/revocation therefore blocks old registrations before reconciliation completes. Agents get read-only identity/diagnostic tools, with no enable/reconnect/install surface. Server text is external untrusted data and does not grant execution or scientific authority.

Live instances retain their actual Cordis fiber before awaiting initial SDK negotiation, allowing disable/disposal to cancel pending startup. Generation checks fence a delayed optional import and stale config. Shutdown closes MCP before project registries/Host grants; the standalone Runtime shutdown owns this too. If transport cleanup fails, the closed-instance approval guard is retained rather than leaving residual tools ungated. Runtime disposal is idempotent. No configured server starts merely because the standalone workbench lists/edits it.

Diagnostics distinguish starting / registered / failed / stopping and report actual currently visible Harness tool names per concrete session. `registered` proves plugin activation completed, not current transport health; reconnect generations can change tool visibility. Error summaries omit resolved credentials and point to Host logs. Resources require the profile's optional/shared `mcpResources` service. Harness owns its SDK timeout, reconnection and protocol limitations; no claim is made for MCP tasks, prompts, subscriptions, OAuth or A2A.

## Verification

Native tests use the actual published plugin against real stdio JSON-RPC and Streamable HTTP fixtures, not SDK mocks: tools/resource reads, named credential delivery without disclosure, project/global scope isolation, denied calls producing no server invocation, explicit approval, immediate durable revocation, reconnect deduplication, real pending-negotiation process exit, delayed import fencing and Runtime-owned shutdown. Registry tests cover CAS, bounded history/discovery, restart, namespaces, copied/rolled-back project authorization and injected Host-grant persistence failure. Owner/CSRF HTTP tests cover standalone storage without network/code execution.

The full published Harness browser fixture enables a connection through the workbench, creates the real Scientist via its formal conversation controller, waits for actual discovery, separately approves Python and MCP tool calls in the main Harness UI, verifies the real server invocation, disables it and reads immutable history. Standalone browser coverage checks missing-adapter labeling, config decisions, credential references, nontransferable export and history after reload. Concrete final full-suite evidence is in IMPLEMENTATION_STATUS.md; remote CI and full Windows/Electron deployment are not inferred from local checks.
