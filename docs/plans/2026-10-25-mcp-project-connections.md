# Project MCP connections

Goal: reuse Harness rc.3 MCP transports, resource service, reconnect supervisor and canonical tool results while adding project-owned configuration, explicit human enablement, diagnostics and scoped Scientist lifecycle management. No second MCP SDK or model loop.

Alternatives: profile-global MCP configuration is already possible but leaks availability across unrelated agents; a standalone OmicOS MCP client duplicates Harness routing/approval and transport semantics. Use immutable project connection revisions plus a Host adapter that mounts the existing `@deepseek-ai/dsh-mcp-client` in each concrete Scientist Agent context, never the shared preset scope.

Implementation sequence:

1. Private project SQLite connection registry: bounded stdio/Streamable HTTP configuration, named Host-environment credential references, default disabled, edit resets enablement, explicit human enable/disable notes, CAS, stable actor-bound operations, immutable history and configuration export without resolved credential values. Current enablement is independently granted by a private Host authorization journal, so copied/restored project files cannot transfer/revive access; cross-database failures revoke first and stay closed. Store creation never spawns a process or sends network requests.
2. Optional exact rc.3 peer Host adapter: concrete `agent/created` / `agent/disposed` lifecycle, per-project namespace isolation, startup/reconnect/disposal generation fences, visible loading/failure/tool-discovery diagnostics, no claimed connection health without transport evidence. Human updates reconcile live project agents; other presets/projects retain no added tools. Require approval for managed MCP tool and resource calls, preserving stronger existing denials.
3. Owner/CSRF workbench management, read-only Agent diagnostics and capabilities. Human confirmation must name external command/endpoint access and data-disclosure scope. Credentials resolve only from explicitly allowlisted Host environment names, never from scientific workers or project plaintext. No auto-install/npm fetching, no automatic tool invocation.
4. Actual MCP fixture over stdio and Streamable HTTP using the published Harness plugin; test scope isolation, approval, credential reference privacy, changed-config deactivation, late startup/disable/dispose, persisted revisions and reload. Browser and full regression checks, documentation and migration status.

Boundaries: enabled records authorize future Scientist attachment in that project; enabling does not independently verify a server's trustworthiness or scientific accuracy. Local servers run with normal Host-user permissions under Harness subprocess behavior. Remote servers can receive explicitly approved arguments/resources. MCP server instructions remain external untrusted data. External profile-managed MCP instances remain owned by Harness and are not modified by this registry. Standalone workbench can manage records but needs the optional Harness adapter to run them. OAuth/A2A, server package installation, MCP tasks/prompts/subscriptions and cross-machine secret synchronization remain separate work.
